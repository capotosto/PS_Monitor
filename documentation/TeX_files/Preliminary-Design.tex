\chapter{Preliminary Design Review}
\label{chap:preliminary-design}

\section{Purpose and Scope}
This chapter documents the preliminary hardware and software design of the
Multi-Rail Isolated Power Supply Monitoring System. The design monitors six
power-supply rails, measures rail voltage and load current, preserves electrical
isolation between floating supplies and the controller, evaluates measurements
against user-configurable alarm limits, presents local status on the controller
display, and publishes measurements and status to an EPICS control-system
interface.

This preliminary design is intended to establish the major analog and digital
functional blocks, document supporting engineering calculations, define the
hardware schematic baseline, and provide software flowcharts detailed enough to
support implementation. Simulation and additional verification results can be
added in the subsequent design phase.

\section{Problem Definition}
The project addresses the need to monitor several low-voltage power-supply rails
that do not necessarily share a common reference. A conventional
monitoring circuit that directly connects the grounds together
would defeat the electrical isolation of the supplies and could create unwanted
return paths. However, the user needs a single location from which to observe rail voltage, rail current, alarm state, communication status, and the overall condition of the power system.

The required monitoring system must therefore make accurate measurements on
six separate rails while preserving isolation between the monitored domains. It
must support both positive and negative rails, detect sensor or communication
faults, provide configurable voltage and current limits, retain configuration
information after reset, present useful local status, and make the same data
available to the facility control system over Ethernet. The monitored rails in
the present design are +5 V A, +5 V B, +/-5 V, and +/-15 V.

\section{Proposed Solution}
The proposed solution assigns one LTC2945 voltage/current monitor to each power
rail. Load current is converted to a small differential voltage by a precision
high-side shunt resistor and the LTC2945 digitizes both the shunt voltage and the
rail voltage. Each sensor remains referenced to its own monitored supply domain.
The I\textsuperscript{2}C communication path is then isolated so that digital
measurement data can be transferred to a common Arduino GIGA R1 WiFi controller
without directly bonding the isolated supply returns together.

The Arduino GIGA performs channel acquisition, engineering-unit conversion,
negative-rail sign handling, alarm evaluation, configuration storage, display
updates, and network communication. A local GIGA Display Shield provides
immediate status at the hardware. Ethernet transports measurement and status
data using the PSC protocol to an EPICS IOC, where PSCDriver and EPICS records
make the values available to a CS-Studio Phoebus operator interface. This
architecture separates the rail-side analog measurement functions from the
controller and supervisory-control functions while maintaining a single user
interface for the complete system.

\section{Chosen Conceptual Design and Functional Block Diagram}
\label{sec:functional-blocks}
The major system functions are summarized below.

\begin{enumerate}
    \item \textbf{Power-Supply Interface:} Connect to the six monitored rails and
    route each rail through the associated voltage/current monitoring channel.
    \item \textbf{Current Measurement:} Convert load current to a differential
    voltage across a precision shunt resistor and digitize it with the
    LTC2945.
    \item \textbf{Voltage Measurement:} Measure the monitored rail voltage using
    the LTC2945 supply-voltage ADC channel.
    \item \textbf{Electrical Isolation:} Maintain galvanic isolation between each
    floating monitored supply and the common controller-side I\textsuperscript{2}C bus.
    \item \textbf{Digital Acquisition:} Poll each monitor, identify communication
    faults, apply channel-specific sign/scaling information, and calculate
    engineering-unit values.
    \item \textbf{Alarm Processing:} Compare voltage and current values against
    configured upper and lower limits and generate channel alarm states.
    \item \textbf{Local User Interface:} Present all rail measurements, alarms,
    network state, and communication status on the Arduino GIGA Display.
    \item \textbf{Network/EPICS Interface:} Publish measurements, alarm limits,
    alarm state, and connection status over Ethernet for the EPICS IOC and
    Phoebus interface.
\end{enumerate}

\section{Design Methodology}
The design was developed by dividing the system into measurement, isolation,
controller, user-interface, and control-system functions and then verifying the
interfaces between those blocks. The analog measurement design began with the
maximum required rail current. The shunt value was selected so that the maximum
nominal current produces a differential voltage comfortably below the LTC2945
102.4 mV current-sense full-scale value. Power dissipation in each shunt was
then calculated using \(P=I^2R\), and the selected resistor rating was checked
against the calculated worst-case dissipation. The same approach was used for
PCB copper: maximum continuous current, allowable temperature rise, and voltage
drop were considered before final trace and copper-pour dimensions were chosen.
Detailed calculations are included in Appendix~\ref{app:design-calculations}.

Electrical isolation was treated as a system-interface requirement rather than
only a component-selection problem. Each LTC2945 remains electrically local to
its rail, and the digital signals cross the isolation boundary through isolated
logic. Controller-side I\textsuperscript{2}C buffering and level compatibility
were checked against 3.3 V logic requirements. The controller does not drive
loads directly; its GPIO and I\textsuperscript{2}C pins only interface to
logic-level circuitry. This substantially reduces the current demanded from an
individual microcontroller pin and allows the high-current rail paths to remain
on the dedicated sensor hardware.

The embedded-software design follows the same functional partitioning. Sensor
acquisition is separated from display formatting, network services, persistent
storage, and PSC message handling. Alarm processing is performed on engineering-unit values after
channel polarity and scaling are applied. The EPICS IOC is intentionally kept
outside the embedded controller so that the Arduino is responsible for hardware
acquisition while the IOC is responsible for exposing process variables to the remote user control system.

\section{Software Architecture and Critical Software Test Results}
\label{sec:software-architecture-tests}
The embedded software is organized into functional modules rather than one
loop. The current implementation contains shared application state,
sensor-management and LTC2945 register-access code, display handling, Ethernet
services, an web control page, PSC protocol handling, persistent storage, and the
main application controller. This separation permits the measurement code to be
tested independently of the EPICS IOC and permits the network/control-system
interface to consume already processed engineering-unit values.

At startup, the firmware initializes hardware interfaces, loads persistent
settings, configures the monitoring channels, and then enters repetitive sensor
acquisition and service processing. Each channel read is checked for successful
I\textsuperscript{2}C communication before conversion. Valid raw ADC values are
scaled using the configured shunt resistance and channel polarity; invalid
transactions produce a communication error state. Voltage and current values
are then compared with their configured lower and upper limits before the local
display and PSC message data are updated. The detailed execution flow is shown
in Appendix~\ref{app:software-flowchart}.

The most critical functions were tested to the extent possible on the available
single-channel evaluation board setup. Sensor acquisition returned stable voltage
and current data, open\slash unconnected channels produced I\textsuperscript{2}C fault
states instead of plausible but invalid values, negative-rail sign handling was
visible on the -5 V test channel, and changing a voltage limit changed the local
alarm state as expected. Ethernet/PSC communication was verified by the EPICS
IOC reporting a connected driver and by Phoebus displaying the same test-channel
voltage/current data. Remaining multi-channel verification, long-duration
operation, restart/persistence checks, and final PCB testing will be repeated on
the assembled production hardware. This is shown in more detail in \nameref{chap:prototyping-dev}

changed from the earliest project documentation. Table~\ref{tab:w2-changes}

        \bottomrule
    \end{tabularx}
\end{table}

The largest remaining technical risk is integration of all six isolated channels
on the final PCB rather than operation of any single functional block. The
single-channel prototype reduced uncertainty in the LTC2945 measurement,
firmware scaling, alarm processing, Ethernet/PSC firmware, and operator interface.
Final verification will focus on channel-to-channel isolation,
concurrent I\textsuperscript{2}C operation, and confirmation that all configured settings survive normal resets and power cycles.
